## 2. 引擎 v2

原則沿用 ARCHITECTURE §4.4：**資料檔不寫腳本**。顯著節點用型別化的觸發與效果描述，zod 驗證；真正改規則的東西才寫成程式裡的規則模組。

### 2.1 傷害標籤

```ts
type DamageTag =
  | 'hit' | 'crit' | 'projectile' | 'chain' | 'area' | 'aura' | 'orbit' | 'strike'
  | 'turret' | 'thorns' | 'trigger' | 'burn' | 'poison' | 'bleed' | 'cold' | 'lightning';
```

- 每次傷害帶一組標籤（bitmask）。修正值依標籤組合計算，**第一次用到某個組合才算，算完快取到這局結束**（天賦在局中不變）。16 個標籤有 65,536 種組合，不能像現在預先全算。
- 修正公式不變：`(base + Σflat) × (1 + Σincreased) × Π(1 + more)`。

### 2.2 發射器（「怎麼打出去」）

| 種類 | 用在 | 說明 |
|---|---|---|
| `volley` | 角色攻擊（現有） | 依攻速射投射物；穿透、彈射、分裂是參數 |
| `orbit` | 光環流派的環繞球 | 繞角色轉，碰到就打；同一隻有命中冷卻 |
| `aura` | 光環 | 固定週期對半徑內的敵人脈衝 |
| `strike` | 落雷、暴風雪、毒爆 | 從天而降打一個區域 |
| `turret` | 砲台 | 有位置的發射器，用角色屬性 × 砲台倍率，帶 `turret` 標籤 |
| `nova` | 新星、尖刺新星、冰霜新星 | 從某一點向外一圈 |
| `thorns` | 荊棘 | 接觸時觸發，不用攻速 |

共同介面：`cadence`（攻速、固定週期或觸發）、`targeting`（最近、最遠、血最多、最密集、自己）、`payload`（傷害倍率、標籤、異常狀態機率、穿透等）。

### 2.3 異常狀態

| 狀態 | 疊加方式 | 實作重點 |
|---|---|---|
| 燃燒（現有） | 有上限的層數 | 不變 |
| 毒 | 無上限、各自計時 | 每隻敵人一個「依到期時間分桶」的環形緩衝：施加時把每秒傷害加進總和與到期那一桶，每 tick 扣掉到期的桶。**層數再多，每 tick 也只算一個數字**。層數也用同樣方式維護，給致死毒素用 |
| 流血 | 只算最強的一個（大出血改成 8 層） | 依敵人這個 tick 有沒有移動決定 ×3 |
| 冰冷／冰凍／碎裂 | 累積值 | 累積到 100% 冰凍；冰凍免疫計時；死亡時若冰凍就碎裂（觸發 `shatter`） |
| 感電 | 有上限的層數 | 受到傷害 +X%／層，計時 |

全部用每隻敵人的欄位存（不是每層一個物件），附近目標查詢沿用現有的空間雜湊格。

### 2.4 觸發與效果（大部分顯著節點靠這個）

```ts
type TriggerSpec = {
  on: 'hit' | 'crit' | 'kill' | 'nthAttack' | 'chainJump' | 'ailmentApplied' | 'diedWithAilment'
    | 'freeze' | 'shatter' | 'heroHit' | 'contact' | 'waveStart' | 'periodic';
  when?: Condition[]; // chance、targetHas、targetKind、targetHpBelow、stacksAtLeast、cooldownSec
  do: EffectSpec[];   // projectiles、nova、explode、applyAilment、spreadAilment、buff、heal、shield、gainShards
};
```

例：M1 的橋接 notable `critIgniteChance` 變成 `{ on: 'crit', when: [{ chance: 0.25 }], do: [{ applyAilment: 'burn' }] }`，不用再寫程式。

**安全規則**（觸發會連鎖，例如爆炸殺怪又觸發爆炸）：

1. 效果進一個先進先出的佇列，依序執行。
2. 每個效果帶「深度」：深度 3 以上的效果不再觸發新的觸發。
3. 同一個觸發造成的傷害不會再觸發它自己。
4. 每 tick 最多執行 2,000 個效果，超過的照順序留到下一 tick，並記錄次數（模擬器報告會列出）。
5. 隨機只從 RNG stream 取，順序就是佇列順序；同時發生的事件依實體 ID 排序。同 seed 兩次結果必須相同（現有的可決定性測試照跑）。

### 2.5 縮放、轉換、規則模組

- **縮放**：「每有 X，得到 Y」。來源：持有碎片、連擊層數、目標毒層、連鎖第幾跳、砲台數、失去的生命、光環內敵人數、和目標的距離；曲線：線性、log10、次方；可設上限。貪婪的 `（持有碎片）^0.12` 就是一條縮放。
- **轉換**：「擊中傷害的 30% 轉成燃燒」。在修正之前套用，合計不超過 100%，轉過去的部分換成新的標籤。
- **規則模組**：關鍵天賦、融合核心、昇華終極、角色招牌攻擊，共約 38 個。每個模組實作需要的掛勾（`compile`、`onAttack`、`onHit`、`onKill`、`modifyDamage`、`tick`），各有單元測試。M1 的 9 條 `RuleSpec`：冷靜狙擊、無盡烈焰、過載、玻璃大砲留做規則模組；熾烈暴擊、瘟疫降級成顯著節點；三個橋接 notable 改成資料觸發或縮放。

### 2.6 系統順序

`simulation.ts` 拆成 `src/sim/systems/*.ts`，每 tick 固定順序：

`input → spawn → enemyAI（衝刺、射擊、召喚、逃走）→ movement → contact（荊棘、漏怪）→ emitters（角色、砲台、光環、環繞、落雷）→ projectiles → hits（含連鎖、轉換、護盾與堅甲、異常狀態、觸發入列）→ ailments → effectQueue（有預算）→ death/drops（擊殺觸發入列）→ waveControl → runEnd`

第一步只拆檔、不改行為，用現有測試和 probe T1–T8 確認結果完全一樣，之後才加新系統。

## 3. 內容資料管線

- **一個流派一個檔**：`src/data/archetypes/<id>.ts`；融合、中央、角色、昇華各自一個檔。
- **模板**：`ranked(stat, perRank, ranks)`、`notable(id, effects)`、`keystone(rule)`、`mastery(tags)`、`threshold(effects)`、`fork(a, b)`。一個流派檔大約 60–100 行。
- **自動排版**：依 game-design-v2 §2 的環狀順序算角度，分支各佔一條放射狀的道，分岔與會合自動排；檢查節點最小間距。排版結果做快照測試，避免改資料時整張網不小心移位。
- **穩定 ID**：`<流派>.<分支>.<名稱>`，例如 `bleed.rend.deep-wounds`。**絕對不用陣列索引**。ID 清單做快照測試：刪掉或改名 ID 時，必須在存檔遷移裡加對照。
- **說明文字自動產生**：依效果描述套 i18n 模板，繁中與英文都要；約 150 個有名字的節點（顯著、關鍵天賦、融合核心、昇華、門檻）手寫名稱。
- **驗證**（CI 擋下）：所有節點從某個起點連得到；每個流派區有入口、三個分支、關鍵天賦、門檻、三個精通；融合只接相鄰流派且入口條件正確；**對照表上每個 ✗ 在該流派區有標 `answers` 的節點**；價格單調遞增；兩種語言的字串都存在。
- **模糊測試**：1,000 組隨機合法配點各跑 60 秒模擬：不當機、沒有 NaN 或 Infinity、效果預算沒有連續爆掉、同 seed 重跑結果相同。

## 4. 規模化平衡

模擬器現有的策略與 T1–T8 保留，新增：

| 檢查 | 標準 |
|---|---|
| 策略 | 12 條純流派、8 個融合、4 個角色的預設 build、「每次買邊際效益最高的節點」、隨機 build；現有的 might-only、balanced、cheapest 保留 |
| 前線節奏 | 每個角色的預設 build 落在 GDD §7.3 時間表 ±15%（表延長到第 100 波） |
| 流派公平 | 12 條純流派到第 20／30／60 波所需時間，最慢 ÷ 最快 ≤ 1.25（現在三條是 1.2） |
| 敵人對照表 | game-design-v2 §5.4：✓ 不快過中位數 0.4 倍；✗ 點了答案節點後在 2.5 倍以內 |
| 融合 | 同樣投入下比較強的母流派強 10–30% |
| 關鍵天賦 | 18 個都照現有 `keystones.ts` 的標準：點了要多 +4～+6 波 |
| 死節點 | 所有策略都沒買過、或每單位價格的效益低於中位數 20% 的節點，列在報告裡 |
| 傳承 | 第二個角色到第 30 波的時間 ≤ 第一個角色的 60% |
| 遊玩時間 | 第一個角色破關 4–6 小時（模擬，含每局之間 20 秒） |

- **怎麼跑**：PR 的 CI 只跑快速子集（3 條純流派＋1 個融合＋煙霧測試）；完整矩陣每天晚上用 GitHub Actions 排程跑，輸出一份 pass／FAIL 表（和現在的 T1–T8 一樣）。
- **成本**：一局 3 分鐘的模擬現在約 25 ms，加了新系統後預算 50 ms；完整矩陣多開 worker 跑，夜間跑得完。

## 5. 存檔 v2

- **帳號**：已解鎖角色、傳承里程碑、設定、統計。
- **每個角色**：配點（含等級）、碎片、核心、最遠波次、轉生次數、累計迴響、昇華選擇、3 組配置。
- **v1 → v2 遷移**：v1 進度變成狙擊手的進度；因為節點 ID 全換，**退還所有花掉的碎片與核心**（等於免費洗點）；最遠波次與統計保留。受影響的只有 Hoshi 和陌生試玩者。
- **從 Demo 開始凍結節點 ID**：之後改名一定要在遷移裡加對照。每個發布過的版本（試玩 v1、Demo）都留一份存檔 fixture 在測試裡。

## 7. 每個流派的完成定義

1. 機制的基本元件做好並有單元測試。
2. 流派區 30 個節點的資料通過驗證，自動排版看起來乾淨。
3. 招牌特效、傷害數字顏色、門檻節點的畫面效果（game-design-v2 §9）。
4. 繁中與英文字串。
5. 模擬器：純流派在節奏範圍內、對照表的答案節點有效、關鍵天賦 +4～+6 波。
6. PR 附一段約第 30 波的 15 秒 GIF（同時是行銷素材）和模擬器報告。
7. **Hoshi 以這個流派為主流派玩 15 分鐘**，同意或給回饋。

## 10. 風險與對策

| 風險 | 對策 |

| 500 節點大多是無聊的 +% | 每個分支 2 個顯著節點、每區一個看得到的門檻節點；死節點報告；Hoshi 15 分鐘試玩 |
