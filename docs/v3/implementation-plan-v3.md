### 2.1 傷害標籤與傷害來源

```ts
type DamageTag =
  // 怎麼送到（傳遞標籤）
  | 'projectile' | 'chain' | 'area' | 'zone' | 'aura' | 'orbit' | 'strike' | 'minion' | 'thorns' | 'trigger'
  // 是什麼傷害（類型標籤）
  | 'hit' | 'crit' | 'burn' | 'poison' | 'bleed' | 'cold' | 'lightning';

type DamageEvent = {
  amount: Num;
  tags: number;      // DamageTag 的 bitmask
  source: SourceId;  // 放出這筆傷害的發射器、規則或效果，例如 'fire.signature'、'outer.aura'、'fusion.fire.ice.core'
};
```

- 17 個標籤。v2 的 `turret` 併進 `minion`（無人機、砲台、靈都算），新增 `zone`（地面區域）。
- 修正值依標籤組合計算，**第一次用到某個組合才算，算完快取到這局結束**（天賦在局中不變）。17 個標籤有 131,072 種組合，不能像 M1 預先全算。
- 修正公式不變：`(base + Σflat) × (1 + Σincreased) × Π(1 + more)`。
- **來源和標籤分開存。** 異常狀態的跳傷依下面的優先順序歸屬：①融合酬載施加的，算那條融合；②其餘依異常狀態的種類：角色自己流派的（熔核的燃燒、霜晶的冰冷與碎裂）算中心，其他種類算給那塊外盤，例如熔核身上的毒算 `outer.poison`、雷塔身上的流血算 `outer.bleed`。直接傷害照放出它的效果算：外盤給的額外連鎖跳、額外小彈算那塊外盤；融合酬載的斬擊線、小彈、電弧、金幣、新星、脈衝區算那條融合；樞紐的擊殺爆炸與新星算樞紐。暴擊、傷害加成這類修正值不改來源。毒（以及無盡烈焰下的燃燒）的分桶依歸屬分開存總和（中心／外盤／融合，每隻敵人最多 3 份）。中心主體性、鏡像融合與結算的傷害組成都用這套歸屬（§4、game-design-v3 附錄 A.4），所以加了轉換或酬載也量得準。

### 2.3 均勻空間格（新，M1 沒有）

- 格子 128 × 128（初始值）。場地 1920 × 1080 是 15 × 9 格；外圍多一圈，給剛生成、還在場外的敵人；更遠的夾到最外圈。
- 每 tick 敵人移動之後重建一次：計數排序寫進平面陣列，不配置新記憶體。
- 查詢：半徑內最近的、半徑內全部、最密集點（3 × 3 格計數）、線段外框經過的格子。同距離依實體 ID 決勝，和現在的 `pickTarget` 一樣。
- 使用者：`pickTarget`、`nearestChainTarget`、`spreadBurns`、爆炸、新星、地面區域、線段、無人機找目標、熔岩彈找最密集點、冰錐的直線碰撞。
- **第一步只換資料結構**：用隨機狀態比對「格子查詢」和「線性掃描」的結果完全一樣，probe T1–T8 的數字不變，才接新系統。

### 2.4 連鎖上限與線段規則（新）

| 規則 | 初始值 | 為什麼 |
|---|---|---|
| 每次攻擊的連鎖命中上限 | 32（所有跳躍與分岔合計） | 分岔、渦流這類規則會讓命中數指數成長 |
| 規則帶來的額外跳 | 每次攻擊合計最多 +2 | 回彈、跳電、導雷等「多跳」疊起來沒有上限 |
| 雷塔「跳躍」事件的酬載 | 每次攻擊最多觸發 3 次 | 每跳 30% 機率，長連鎖時不會洗版 |
| 線段傷害 | 只連最近的配對，每 0.25 秒判定一次 | v2 的雷網是感電敵人兩兩相連，O(k²) |

- **雷網**（雷塔門檻）：每隻感電的敵人只連到 200 內最近的 2 隻感電敵人，重複的配對去掉，所以線段數 ≤ 2 × 感電敵人數。
- **雷召喚「雷網蜂」**：每架無人機只連到離它最近的一架。
- **雷射柵欄**（召喚外盤門檻）：每個召喚物只連到離它最近的另一個。
- **判定**：只查線段外框經過的格子；離線段的距離 ≤ 敵人半徑就受傷（含線段兩端的敵人），10% 擊中傷害並感電（初始值）。每隻敵人每次判定最多算一次，壓在幾條線上都一樣。

### 2.5 異常狀態

| 狀態 | 疊加方式 | 實作重點 |
|---|---|---|
| 燃燒（M1） | 有上限的層數；無盡烈焰下沒有上限 | 有上限時沿用 M1 的每層記錄（最多十幾層，需要「換掉最弱的一層」）。**無盡烈焰下改用和毒一樣的分桶環形緩衝**，層數只是一個數字。瘟疫、燎原、引爆、雷火「引信」與火毒的覆寫一律搬「總和」：傳出去的是每一桶的每秒傷害 × 比例，不是一層一層複製。找目標時的「燒得死嗎」也只讀總和。無盡烈焰下，引爆的「層數滿」改成「≥ 5 層」 |
| 毒 | 無上限、各自計時 | 每隻敵人一個「依到期時間分桶」的環形緩衝：每 0.25 秒一桶，共 64 桶（最長 16 秒），更長的持續時間夾到 16 秒。施加時把每秒傷害加進總和與到期那一桶，每 tick 扣掉到期的桶。**層數再多，每 tick 也只算一個數字**。層數也用同樣方式維護，給致死毒素用 |
| 流血 | 只算最強的一個（大出血改成 8 層） | 依敵人這個 tick 有沒有移動決定 ×3 |
| 冰冷／凍結／碎裂 | 每隻敵人一個冰冷量表 0–100% | 減速隨量表增加，上限沿用（一般 30%、Boss 15%）。一般敵人到 100% 凍結 1.2 秒，之後 3 秒免疫。**Boss 不會凍結，但到 100% 仍然觸發「凍結」事件，然後量表歸零，之後 4.2 秒不再累積**（等於一般敵人的凍結＋免疫），所以冰的融合打 Boss 也有效，但不會比打一般敵人更頻繁。絕對零度拿掉一般敵人的免疫時間，但 Boss 的凍結事件仍至少間隔 1 秒。凍結中死亡會碎裂（觸發 `shatter`） |
| 感電 | 有上限的層數 | 受到傷害 +X%／層，計時 |

除了有上限的燃燒（沿用 M1 的每層記錄），全部用每隻敵人的欄位存，不是每層一個物件；每隻敵人每 tick 的計算量和層數無關。附近目標查詢走 §2.3 的空間格。

### 2.6 觸發與效果（大部分顯著節點靠這個）

```ts
type CenterEvent = 'explode' | 'freeze' | 'chainJump' | 'droneImpact';

type TriggerSpec = {
  on: CenterEvent
    | 'hit' | 'crit' | 'kill' | 'nthAttack' | 'ailmentApplied' | 'diedWithAilment'
    | 'shatter' | 'heroHit' | 'contact' | 'waveStart' | 'periodic' | 'droneExpire';
  when?: Condition[]; // chance、targetHas、targetKind、targetHpBelow、stacksAtLeast、cooldownSec
  do: EffectSpec[];   // 見下表
};
```

例：M1 的橋接 notable `critIgniteChance` 變成 `{ on: 'crit', when: [{ chance: 0.3 }], do: [{ applyAilment: 'burn' }] }`，不用再寫程式。

v2 已有的效果：`projectiles`、`nova`、`explode`、`applyAilment`、`spreadAilment`、`buff`、`heal`、`shield`、`gainShards`。v3 新增：

| 效果 | 用在 |
|---|---|
| `spawnDrone` | 召喚酬載的 4 秒小無人機、分巢、火靈、電蜂、冰晶哨 |
| `chainBolt` | 雷酬載的 2 跳電弧；手工融合（電漿、超導）也呼叫它 |
| `groundZone` | 熔岩彈的火地、霜焰、光環酬載的脈衝區、毒雲 |
| `slashLine` | 暴擊酬載：必定暴擊的斬擊線 |
| `coinHit` | 貪婪酬載：10 倍擊中、無視護盾、不花碎片 |
| `addFrost` | 冰酬載、冰鏈、霜焰 |
| `comboStack` | 連擊酬載 |
| `push` | 熔核「熱浪」：`dist += 80` |

**安全規則**（觸發會連鎖，例如爆炸殺怪又觸發爆炸）：

1. 效果進一個先進先出的佇列，依序執行。
2. 每個效果帶「深度」：深度 3 以上的效果不再觸發新的觸發。
3. 同一個觸發造成的傷害不會再觸發它自己。
4. 每 tick 最多執行 2,000 個效果，超過的照順序留到下一 tick，並記錄次數（模擬器報告會列出）。
5. 隨機只從 RNG stream 取，順序就是佇列順序；同時發生的事件依實體 ID 排序。同 seed 兩次結果必須相同（現有的可決定性測試照跑）。
6. 地面區域、召喚物、投射物與延遲出手的效果（例如殘影的 0.3 秒）都記住建立它的那個效果的深度與觸發；它們造成的傷害與觸發從那個深度往下算，不會歸零，第 3 條也照這個出處判斷。
7. 重複出來的攻擊（回聲、殘影、多重施法多放的 2 次）不算進「每第 N 次攻擊」的計數，也不會再被重複。
8. 中心事件只由招牌攻擊本身觸發：熔核只算熔岩彈（含火山與遠投）落地，連環爆、擊殺爆炸、焚屍與融合放出的爆炸都不算；雷塔只算三相雷的跳，融合與覆寫放出的閃電不算；蜂巢只算無人機撞擊。霜晶的凍結不限冰冷來源，但受第 2、6 條限制。

### 2.7 縮放、轉換、規則模組

- **縮放**：「每有 X，得到 Y」。來源：持有碎片、連擊層數、目標毒層、目標冰冷量表、連鎖第幾跳、召喚物數量、失去的生命、光環內敵人數、和目標的距離。曲線：線性、log10、次方；可設上限。貪婪的 `（持有碎片）^0.12` 就是一條縮放。
- **轉換**：「擊中傷害的 30% 轉成燃燒」。在修正之前套用，合計不超過 100%。**v3 改一條**：轉過去的部分只換掉類型標籤（例如 `hit` 換成 `poison`），傳遞標籤與來源保留。例：蜂巢的無人機傷害有一部分轉成毒，那部分仍然帶 `minion`，蜂巢中心盤的「無人機傷害 +%」照樣有效。v2 的寫法會讓那部分失去 `minion`，召喚角色的加成整個失效。模板融合完全不用轉換（§2.12）。
- **規則模組**：每個模組實作需要的掛勾（`compile`、`onAttack`、`onHit`、`onKill`、`onCenterEvent`、`modifyDamage`、`tick`），各有單元測試。

| 規則模組 | 數量 | 說明 |
|---|---|---|
| 招牌攻擊 | 4 | 熔岩彈、冰錐扇、三相雷、蜂群 |
| 中心盤 ★ | 8 | 每個角色 2 個，包括 M1 的無盡烈焰、過載 |
| 外盤 ★ | 12 | 火、冰、雷、召喚 4 個外盤的 ★ 重用中心模組（無盡烈焰、絕對零度、過載、蟲海）；暴擊外盤的 ★ 是 M1 的冷靜狙擊 |
| 樞紐 ★ | 2 | 玻璃大砲（M1）、巨大化 |
| 手工融合核心 | 12 | 4 個角色流派之間的融合（game-design-v3 §5.2） |
| 昇華終極 | 8 | 每個角色 2 個 |
| **合計** | **46** | 不重複的 42 個；M1 已有 4 個（無盡烈焰、過載、玻璃大砲、冷靜狙擊），**新寫 38 個**，和 v2 一樣多 |

M1 的 9 條 `RuleSpec`：冷靜狙擊、無盡烈焰、過載、玻璃大砲留做規則模組；瘟疫降級成熔核擴散分支的顯著節點；熾烈暴擊（critsAlwaysIgnite）在 v3 沒有對應節點（暴擊外盤沒有保留 v2 的暴擊觸發分支），規則刪掉；三個橋接 notable（`critIgniteChance`、`chainIgniteChance`、`chainCritChance`）改成資料觸發或縮放。

### 2.8 地面區域（新）

```ts
type GroundZone = {
  id: number;
  x: number; y: number; radius: number;
  expiresAt: number;
  pulseEvery: number;            // 0.25 秒
  effects: readonly EffectSpec[]; // 每秒傷害％、上異常狀態、減速
  tags: number;                  // 帶 'zone'
  source: SourceId;
};
```

- 一個系統給所有「留在地上」的東西用：熔岩彈的火地（1.5 秒、每秒 30%）、霜焰的霜火地（減速 30%）、毒雲、光環酬載的 2 秒脈衝區。
- 每 0.25 秒脈衝一次，用空間格查範圍內的敵人，不每 tick 掃全場。每個區域的脈衝相位錯開，不會擠在同一個 tick。
- 同時最多 64 個（初始值），每個來源最多 16 個。招牌攻擊自己的地面區域（熔核的火地）不算在 64 裡，另有上限 16。超過時先移除同一個來源最舊的。

### 2.9 無人機與召喚物（新）

**限制**（game-design-v3 §1.6；同樣寫進 CLAUDE.md，不能在批次裡放寬）：

| 限制 | 內容 |
|---|---|
| 沒有生命 | 不會被打壞；靈和臨時無人機用存在時間代替生命 |
| 不尋路 | 直線移動，穿過一切 |
| 不被瞄準 | 敵人永遠不打召喚物，也不會被它們擋住 |
| 不碰撞 | 召喚物之間、召喚物和敵人之間都沒有碰撞；撞擊只是距離判定 |
| 更新順序 | 依實體 ID，保證可決定性 |
| 找目標 | 每 0.5 秒才重新找一次。例外：守衛模式的無人機在衝刺者開始蓄力的那個 tick 就換目標（事件觸發）。已經有無人機在追的敵人排在後面（和 M1 投射物的 inbound 一樣） |
| 數量 | 全場上限 24，臨時的也算。滿了就不再生新的，模擬器報告記次數 |
| 統一實作 | 砲台＝速度 0 的無人機；靈＝有壽命的無人機 |

```ts
type DroneState = {
  id: number;                      // 實體 ID，也是更新順序
  kind: 'drone' | 'turret' | 'spirit';
  mode: 'docked' | 'dash' | 'return' | 'guard' | 'fixed';
  x: number; y: number;
  speed: number;                   // 蜂巢無人機 600；砲台 0
  dockTime: number;                // 停靠時間，初始 0.5 秒，除以攻擊頻率倍率
  attack: 'impact' | EmitterRef;   // 撞擊，或從自己的位置呼叫一般發射器（砲台、冰晶哨、電蜂）
  targetId: number;                // -1＝沒有目標
  nextRetarget: number;            // 每 0.5 秒
  impactsLeft: number;             // 撞 3 次後回巢
  lastHitId: number;               // 同一隻 0.5 秒內不再撞
  lastHitAt: number;
  expiresAt: number;               // 靈與臨時無人機；常駐的是 Infinity
  damageMult: number;              // 蜂巢：撞擊 2、砲台 0.8（授予的無人機：0.8、0.4）
  skins: readonly OuterId[];       // 最多 3 個，依融合槽順序：第 1 個換填色，第 2 個換拖尾，第 3 個換撞擊特效
  source: SourceId;
};
```

- **蜂巢的無人機**（初始值，規格見 game-design-v3 §1.5）：停在蜂巢外圈的停靠環；出擊時以速度 600 衝向目標，場地內沒有射程限制，優先打外圈的敵人（`dist` 最大，極座標下很便宜）；撞擊造成 200% 傷害加半徑 40 的濺射；同一隻 0.5 秒冷卻；撞 3 次回巢。只打場地內的敵人。已經有無人機在追的敵人排在後面，3 架不會一起撞同一隻。
- **攻擊頻率對無人機**：衝刺速度與回巢速度乘上攻擊頻率倍率，停靠時間（`dockTime`，初始 0.5 秒）與同一隻的撞擊冷卻（0.5 秒）除以這個倍率。例：攻擊頻率 +50% → 速度 ×1.5、停靠 0.33 秒。砲台照一般發射器。
- **砲台**：固定在半徑 90，80% 傷害、50% 攻速，從自己的位置呼叫 `volley`。
- **守衛模式**：攔截守衛的 2 架在半徑 120 繞行，優先打正在蓄力的衝刺者。衝刺者開始蓄力的那個 tick 就換目標（事件觸發），不等 0.5 秒的找目標週期。
- **外觀**：無人機是實心、發亮邊、頭朝外的箏形；敵人是空心、半透明、頭朝內（game-design-v3 §11）。外觀只在 render。

|---|---|---|---|---|

| 霜晶 | `freeze` 凍結 | 冰冷量表到 100%（Boss 也算） | 目標與半徑 90 內最多 5 隻 | 落點類酬載以目標為中心放 1 次；酬載每秒最多 8 次（初始值），超過的凍結照常凍住，但不放酬載 |

- **`overrides.ts`** 逐條覆寫：12 條手工融合的核心指向規則模組；其他融合可以改數值、文字、外觀，或把核心換成另一組資料觸發。v2 的規則照這樣重用：瘟疫爆彈成為火毒的覆寫、永凍成為冰光的覆寫、雷暴環成為雷光的覆寫（光環的簡稱用「光」，避免和熔核門檻「火環」撞名，見 game-design-v3 §5.1）。
- **名稱自動產生**：中心在前（冰火、冰毒）；蜂巢用 Hoshi 的說法「X召喚」（火召喚、冰召喚、毒召喚）；元素角色接召喚外盤叫「X靈」（火靈、冰靈、雷靈）；光環的一字簡稱是「光」（火光、冰光、雷光），避免和熔核門檻「火環」撞名。44 個稱號手寫：模板融合一律兩個字，手工融合裡冰晶哨、雷網蜂是三個字。
- **係數校準**：模擬器用二分法把每條融合（含 12 條手工）的 `coef` 調到比基準強 +20%（量法見 §4 的融合強度），結果寫進自動產生、進版控的 `src/data/fusion/calibrated.ts`。

### 2.13 角色定義（新）

### 2.15 系統拆分與 tick 順序

`simulation.ts` 拆成 `src/sim/systems/*.ts`，每 tick 固定順序：

`input → spawn → enemyAI（衝刺、射擊、召喚、逃走）→ movement（只有敵人，角色不動）→ grid（重建空間格）→ contact（荊棘、漏怪）→ emitters（招牌攻擊、光環、環繞、落雷、新星）→ drones（依實體 ID：找目標、移動、撞擊）→ projectiles（含熔岩彈落地、冰錐碰撞）→ segments（每 0.25 秒）→ groundZones（每 0.25 秒脈衝）→ hits（連鎖與上限、轉換、護盾與堅甲、異常狀態、中心事件與觸發入列）→ ailments → effectQueue（有預算）→ death/drops（擊殺觸發入列）→ waveControl → runEnd`

- projectiles、segments、groundZones 的命中當下就結算（hits 是共用的函式，不是另一個階段）。擊殺也當下處理，和 M1 的 `killEnemy` 一樣：移出目標查詢、瘟疫擴散、掉落、分裂，分裂出來的敵人同一 tick 後面的命中就打得到。只有新的資料驅動擊殺觸發（`on: 'kill'`、`diedWithAilment`）在 death/drops 這一步入列。這樣第一步拆檔時結果才會和 M1 完全一樣。
- 第一步只拆檔、不改行為，用現有測試和 probe T1–T8 確認結果完全一樣。第二步換空間格，結果仍然完全一樣。之後才加新系統。
- 同一 tick 裡被熱浪推開的敵人，下一 tick 才更新格子。

## 3. 內容資料管線

**檔案結構**：

```
src/data/
  characters/          fire.ts、ice.ts、lightning.ts、summon.ts
                       每檔：CharacterDef、中心盤 40 個節點、2 個昇華 × 3
  outer/               bleed、crit、barrage、combo、lightning、aura、ice、fire、poison、greed、summon、thorns（各一個 .ts）
                       每檔：外盤 18 個節點、酬載、點綴色與形狀、能補哪些敵人
  hub.ts               樞紐環 24 個節點
  fusion/
    generate.ts        中心事件 × 外盤酬載 → 44 條 × 5 個節點
    overrides.ts       12 條手工融合，以及個別的數值、文字、外觀覆寫
    calibrated.ts      模擬器校準的係數（自動產生，進版控）
  web/
    assemble.ts        組出某個角色的網（323 個節點）
    layout.ts          自動排版
  templates.ts         ranked、notable、keystone、mastery、threshold、gate、entry
```

- **模板**：`ranked(stat, perRank, ranks)`、`notable(id, effects)`、`keystone(rule)`、`mastery(tags)`、`threshold(effects)`、`gate()`、`entry(source)`。外盤檔約 60–90 行，角色檔約 150–200 行（推論）。
- **穩定 ID**，**絕對不用陣列索引**：

| 區塊 | 格式 | 例子 |
|---|---|---|
| 中心盤 | `<char>.center.<branch>.<name>` | `fire.center.spread.pandemic` |
| 樞紐環 | `hub.<group>.<name>` | `hub.defense.second-life` |
| 外盤 | `outer.<arch>.<branch>.<name>` | `outer.poison.contagion.toxic-cloud` |
| 融合 | `fusion.<char>.<outer>.<slot>` | `fusion.fire.poison.core`、`fusion.summon.ice.r2` |
| 昇華 | `<char>.asc.<name>.<slot>` | `fire.asc.incinerator.final` |

  ID 清單做快照測試：刪掉或改名 ID 時，必須在存檔遷移裡加對照。
- **自動排版**：中心盤 3 個分支以 120° 放射，招牌攻擊在正中，★ 與門檻在外緣，6 個接口接樞紐環；外面是 12 個固定鐘點（§2.14）與輻條（樞紐環直通外盤入口，融合分支掛在旁邊）。還沒投資的外盤要能畫成收合的小圓，排版同時算展開與收合兩種。檢查節點最小間距。4 個角色各一份排版快照，避免改資料時整張網不小心移位。
- **說明文字自動產生**：依效果描述套 i18n 模板，繁中與英文都要。約 170 個有名字的節點（招牌攻擊、顯著、關鍵天賦、門檻、昇華）手寫名稱；44 條融合的名稱自動產生，稱號手寫。外盤預覽卡「接到你的角色會得到什麼」也由酬載和這個角色的中心事件自動產生。
- **驗證**（CI 擋下）：
  - 所有節點從招牌攻擊連得到；節點總數與每個角色看得到的數量，等於已經做好的區塊照 game-design-v3 §2.1 算出來的值（中心盤 40、樞紐環 24、外盤 18、融合 5、昇華 3）。Demo 旗標開著時是 246／每個角色 162；全部做完（B5 起）是 644／每個角色 323。§8.1 的每批累計（156、246、405、632、644）當對照。
  - 每塊外盤的入口不經過融合節點也連得到樞紐環。
  - **買得到**：從空網開始，只照買點規則（相鄰、中心門檻、外盤門檻、融合解鎖、融合槽、關鍵天賦上限）一個一個買，每個角色看得到的每個節點都要能在某個合法配點裡買到。融合槽與關鍵天賦有上限，不會同時持有全部節點，所以逐條融合、逐個關鍵天賦分別驗證；昇華節點在轉生後的狀態驗證。Demo 旗標開著時也一樣。只檢查連得到不夠：外盤如果只能經過融合分支走到，而融合核心又要外盤 ≥ 6，就永遠點不到。
  - 每個中心盤有招牌攻擊、3 個分支各 10 個、2 個 ★、門檻、6 個接口；每塊外盤有入口、2 個分支各 7 個、答案節點、★、門檻。
  - 已經做好的角色與外盤之間的融合都在（B4 起 44 條、每個角色 11 條），沒有自己流派那一條；ID 符合 `fusion.<char>.<outer>.<slot>`；解鎖條件正確（中心 ≥ 8、外盤 ≥ 6）。
  - 每個角色檔的流派在它固定的鐘點（火 12、雷 3、冰 6、召喚 9）。
  - 每個角色對照表上的每個 ✗（寶藏怪除外），在那個角色的中心盤有標 `answers` 的節點；每塊外盤標了能補哪些敵人。
  - 價格單調遞增；兩種語言的字串都存在，包括融合名稱與稱號。
- **模糊測試**：1,000 組隨機合法配點（遵守相鄰、融合槽、關鍵天賦上限）各跑 60 秒模擬：不當機、沒有 NaN 或 Infinity、效果預算沒有連續爆掉、召喚物不超過 24、敵人不超過 400、投射物不超過 512、連鎖命中不超過 32、同 seed 重跑結果相同。隨機配點有一部分用 3 個融合槽，三融合的溢位在 PR 就抓得到。另外固定跑一個案例「熔核：瘟疫＋無盡烈焰＋悶燒，第 30 波清怪」。PR 的 CI 就跑（推論約 10–20 秒）。

| 效能 | §6 的一般一局與壓力場景預算；和同一個 job 的參考時間比，超過基準比值 1.5 倍 CI 失敗 | PR |

- **怎麼跑**：PR 的 CI 只跑快速子集（已經做好的角色的預設 build、1 條手工融合、1 條模板融合、新手公平、中心主體性、模糊測試、效能）。完整矩陣每天晚上用 GitHub Actions 排程跑，輸出一份 pass／FAIL 表（和現在的 T1–T8 一樣）。
- **成本**：一局 3 分鐘的模擬現在約 25 ms，加了新系統後預算 50 ms。220 組雙融合約 45 分鐘（2 核 runner，推論）；660 組三融合約 2.5 小時，每週跑一次，在 GitHub Actions 單一 job 6 小時的上限內。Repo 是公開的，GitHub Actions 分鐘數免費。

## 6. 效能預算

| 項目 | 預算 |
|---|---|
| 模擬一局 3 分鐘 | bench 的工作量平均 ≤ 50 ms（現在約 25 ms），等於每 tick 平均約 4.6 µs |
| 壓力場景（模擬） | 固定 30 秒（1,800 tick）的合成場景：全程維持約 300 隻敵人存活（波次放大、角色生命極大）、召喚物 32 個（24 架無人機＋8 座砲台，比全場上限 24 多三分之一，留餘裕）、地面區域、雷網全開，每局 ≤ 50 ms（每 tick 約 28 µs，初始值）。M1 在約 300 隻存活時實測每 tick 7–13 µs（3 分鐘一局要 84–135 ms），新系統約再加一倍（推論），所以壓力場景不能用 3 分鐘一局 |
| 壓力場景（異常狀態） | 固定案例「熔核：瘟疫＋無盡烈焰＋悶燒，第 30 波清怪」，同樣 30 秒、≤ 50 ms。M1 的每層燃燒寫法在這個案例一局要約 5.7 秒，所以無盡烈焰下一定要用分桶（§2.5） |
| 壓力場景（畫面，60 fps，Hoshi 的電腦；Steam Deck 上市後再驗，CLAUDE.md 不做清單） | 模擬的壓力場景，再加兩圈共 8 顆環繞球、光環、Boss 身上 500 層毒 |
| 異常狀態 | 每隻敵人每 tick 的計算量和層數無關 |
| 場上敵人 | 同時最多 400 隻（初始值）。到上限時，波次的生成往後延，召喚者與母巢那一次不生；模擬器報告記次數 |
| 投射物 | 全場最多 512 發（初始值），到上限時新的小彈不生、記次數；小彈壽命 2 秒 |
| 空間格 | 每 tick 重建一次、不配置記憶體；格子 128 |
| 連鎖 | 每次攻擊最多命中 32 隻，額外跳最多 +2 |
| 線段、地面區域 | 只連最近的配對；每 0.25 秒判定或脈衝，相位錯開；地面區域最多 64 個、每個來源最多 16 個，招牌攻擊的火地另計、上限 16（§2.8） |
| 召喚物 | 全場上限 24；每 0.5 秒才重新找目標 |
| 效果佇列 | 每 tick 最多 2,000 個效果，深度 3 |
| 傷害數字 | 持續傷害每隻敵人每 0.5 秒合併成一個數字；畫面上最多約 80 個；暴擊與數字里程碑一定顯示 |
| 粒子 | 物件池，每個角色與外盤有上限 |
| 選角畫面 | 4 張卡同時跑固定 seed 的 10 秒循環，維持 60 fps；做不到就只讓游標所在的那張動 |

CI 在同一個 job 先跑一次 M1 bench 的工作量當參考；各場景（一般一局與壓力場景）的時間 ÷ 參考時間，超過記錄下來的比值 1.5 倍才失敗。不比絕對毫秒，因為共用 runner 的速度會差很多。

## 7. 完成定義

**每個角色**（中心盤＋外觀）：

1. 招牌攻擊與中心事件有單元測試，含可決定性。
2. 中心盤 40 個節點與 2 個昇華通過驗證，自動排版乾淨（快照）。
3. 構造體、場地、攻擊語言、門檻的畫面效果、傷害數字顏色（game-design-v3 §11）。渲染位移 ≤ 40 px，碰撞半徑維持 30（`PLAYER_RADIUS` 不變）。
4. 選角卡：難度星、擅長與怕的敵人圖示、10 秒固定 seed 預覽。
5. 繁中與英文字串。
6. 模擬器：前線節奏、新手公平與角色公平（和已經做好的角色比，B4 起 4 個角色全比）、敵人對照表那一列、中心主體性 ≥ 50%、兩個 ★ 各 +4～+6 波。
7. PR 附一段約第 30 波的 **15 秒 GIF**（同時是行銷素材）和模擬器報告。
8. **Hoshi 用這個角色玩 15–20 分鐘**，同意或給回饋。

**每塊外盤**：

1. 18 個節點通過驗證：入口（給任何角色這個流派的基本來源，例如點燃機率、+1 架無人機）、2 個分支、答案節點、★、門檻。
2. 酬載、點綴色與形狀語言。和某個角色主色的 OKLCH 色相相差 30° 以內時（game-design-v3 §11.6），用形狀區分（例如彈幕的細長子彈對熔核的圓形熔岩彈）。
3. 預覽卡文字：「接到你的角色會得到什麼」、能補哪些敵人。
4. 繁中與英文字串。
5. 模擬器：能補的敵人確實改善（清完的時間或受到的傷害，§4）、死盤報告、★ +4～+6 波。
6. ★ 和中心共用模組的（火、冰、雷、召喚），由先做到的那一批寫模組。例：冰外盤在 B1，所以絕對零度在 B1 就要寫。
7. 審查：片段牆＋模擬器報告。Hoshi 不另外玩，會在角色試玩時碰到。

**每條融合**：

| | 手工（12 條） | 模板（32 條） |
|---|---|---|
| 規則 | 規則模組＋單元測試 | 產生器輸出、通過驗證；需要時用 `overrides.ts` 覆寫 |
| 2 秒規則 | 核心點下去 2 秒內，畫面上看得出差別 | 同左，靠外盤的點綴色、形狀與酬載特效 |
| 強度 | 校準到 +20%，每個 seed 都在 10–30% | 同左 |
| 鏡像 | 和它的鏡像比傷害組成 | 沒有鏡像，不比 |
| 外觀 | 手工特效與皮膚 | 外盤的點綴色與形狀參數，不寫新特效 |
| 字串 | 名稱自動、稱號與說明手寫 | 名稱與說明自動、稱號手寫 |
| 審查 | GIF；**Hoshi 每條玩 5 分鐘** | 自動剪的 **3 秒片段**放進片段牆；Hoshi 看片段牆＋模擬器報告 |

**片段牆工具**（引擎期做）：開發用頁面，用固定 seed、指定 build、指定波次重播每條融合的 3 秒，並排顯示；和選角畫面的 10 秒預覽共用同一個重播元件。模擬是純的，不用真的錄影。
